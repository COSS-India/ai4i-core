API Key Allocation & Reallocation

How a percentage of an Application's budget is granted to an individual API key at creation, re-sliced later without breaking siblings, and kept honest across two databases that don't share a transaction.

00Where this departs from the shared artifact

The Application Onboarding artifact this builds on has changed shape twice while this was being written — basis points, then absolute ceilings, then a percentage-plus-derived-amount hybrid — and its key-level detail hasn't caught up with its own schema. Rather than inherit the gaps, the four calls below are made explicitly here and carried through the rest of this document.

Open question in the sourcePosition taken here
api_key.application_id shown as unconditionally NOT NULL, no admin exception Kept mandatory for every key. The adopter-admin exception moves to a seeded System Application per platform, rather than a nullable column — see II.1.
api_key.user_id removed, ownership model unstated Replaced with created_by — audit only. Management rights come from the caller's role over the Application's Institution, not from having created the row.
budget_usage grained per key only, no tenant/application column Kept as-is; Application and Institution totals are always a roll-up over their keys' rows, never stored redundantly. See II.1.
"auth unreachable, core up" left as an open question Resolved: billing enforcement never depends on auth being reachable. Only administration — creating or editing an allocation — does. See II.5.

Part I

IHigh-level design

I.1Actors and goal

An Institution Admin slices an Application's budget across the keys that draw on it. An Adopter Admin does the same inside the platform's own System Application. Both need three guarantees: a key's slice can never make its siblings overcommitted, a slice can never be cut below what its key has already spent, and two admins editing at once can never both succeed into an invalid total.

01

Percentage in, amount cached

An admin always enters a share of the parent. The system derives and stores a currency figure alongside it, so billing never has to do that arithmetic per request.

02

One ceiling, one ledger

The ceiling lives beside the key's identity in auth. What it has actually spent lives in core, in exactly one place, and is never duplicated as a second stored counter.

03

A snapshot bridges the two

Core keeps a copy of the ceiling so billing reads one database, not two. Every allocation write refreshes that copy; a reconciliation sweep bounds how stale it can ever get.

I.2Design decisions

Decision

Percentage is the source, amount is derived, both are stored. Admins reason in shares of a parent; billing needs a plain number to compare against spend. Storing both on the same row means neither has to be recomputed on the request path — only on the (rare) admin write path.

Decision

Every application has a home, including test keys. No key is ever created without an application_id. Unattached, ad-hoc keys are keys inside a seeded System Application that carries no ceiling of its own — the same escape hatch the "Default" Application already provides for pre-existing keys, reused rather than reinvented.

Decision

Revoking a key freezes its slice; releasing it is a separate, explicit action. A revoked key keeps its historical spend and its allocation until an admin deliberately releases the slice back to the Application. This stops budget from being reclaimed by revoke-and-recreate, without permanently stranding it either.

I.3System diagram

Ceilings are set and read in auth, alongside the identities they belong to. Spend is recorded and read in core, alongside the ledger it has always lived in. The snapshot is the only thing that ever crosses.

I.4Create & reallocate, at a glance

  • Create: pick an Application, optionally hand the new key a percentage of it. The system checks siblings still fit inside 100%, then writes the key and mirrors its ceiling into core.
  • Reallocate: change one key's percentage. The system checks siblings again, checks the new ceiling still covers what's already been spent, then writes and re-mirrors.
  • Release: a revoked key's frozen slice is returned to the Application's headroom on request, never automatically.

Because budget_usage carries no application_id, computing an Application's total spend means first listing its key ids in auth, then summing consumed for those ids in core — a cross-database step on every roll-up read, not only on the billing write path. Acceptable for an admin-facing dashboard refreshed occasionally; worth a second look if it ever needs to be near-real-time.

II.2Deriving and propagating an amount

An amount is only ever computed one level at a time, downward:

application.allocated_budget = tenant.allocated_budget      × application.allocation_pct / 100
key.allocated_budget         = application.allocated_budget × key.allocation_pct / 100

Whichever level changes — the tenant's total, an Application's own percentage, or a key's percentage — recomputes everything beneath it, in the same transaction, before that transaction commits. A tenant budget change therefore fans out to every Application and every key underneath it in one pass; expected to be tens of rows, not thousands, so the cost is a non-issue.

Algorithm

fn createApiKey(tenantId, applicationId, allocationPct, callerId):
    application = auth.get(applicationId)
    require application.tenant_id == tenantId          # cross-tenant guard

    with auth.advisory_lock("app-alloc:" + applicationId):
        siblings = auth.sum(allocation_pct WHERE application_id = applicationId
                             AND is_active)
        if allocationPct is not NULL and siblings + allocationPct > 100:
            raise ALLOCATION_TOTAL_EXCEEDED

        budget = derive(application.allocated_budget, allocationPct)
        key = auth.insert(api_key, application_id, allocationPct, budget,
                           is_active=true, version=1, created_by=callerId)
        # lock releases on commit

    syncPending = not core.try_upsert(budget_usage,
                                       api_key_id=key.id,
                                       ceiling_snapshot=budget,
                                       ceiling_snapshot_version=1,
                                       consumed=0)
    return key, syncPending

II.4Reallocate — sequence and algorithm

sequenceDiagram
    participant Admin
    participant Auth as auth-service
    participant AuthDB as auth DB
    participant CoreDB as core DB
    Admin->>Auth: PATCH /api-keys/{id}/allocation { allocationPct, expectedVersion }
    Auth->>AuthDB: pg_advisory_xact_lock("app-alloc:"+applicationId)
    Auth->>AuthDB: SELECT api_key FOR UPDATE
    Auth->>Auth: version matches expectedVersion?
    Auth->>AuthDB: SUM(allocation_pct) over other active siblings
    Auth->>Auth: siblings + new ≤ 100?
    Auth->>CoreDB: read consumed for this key
    CoreDB-->>Auth: consumed
    Auth->>Auth: new ceiling ≥ consumed?
    Auth->>AuthDB: UPDATE api_key (version += 1)
    AuthDB-->>Auth: committed — lock released
    Auth->>CoreDB: UPDATE budget_usage.ceiling_snapshot, ceiling_snapshot_version
    Auth-->>Admin: 200 OK

Algorithm

fn reallocate(keyId, newPct, expectedVersion):
    with auth.advisory_lock("app-alloc:" + key.application_id):
        key = auth.get(keyId, FOR_UPDATE)
        if key.version != expectedVersion:
            raise ALLOCATION_VERSION_CONFLICT

        siblings = auth.sum(allocation_pct WHERE application_id = key.application_id
                             AND is_active AND id != keyId)
        if newPct is not NULL and siblings + newPct > 100:
            raise ALLOCATION_TOTAL_EXCEEDED

        newBudget = derive(application.allocated_budget, newPct)
        consumed  = core.read(budget_usage.consumed WHERE api_key_id = keyId)
        if newBudget is not NULL and consumed > newBudget:
            raise ALLOCATION_BELOW_CONSUMED(consumed, newBudget)

        key.allocation_pct, key.allocated_budget = newPct, newBudget
        key.version += 1
        auth.commit()

    syncPending = not core.try_update(budget_usage,
                                       api_key_id=keyId,
                                       ceiling_snapshot=newBudget,
                                       ceiling_snapshot_version=key.version)
    return key, syncPending

II.5Concurrency and the cross-database gap

Two admins, one Application: every create or reallocate under the same Application takes the same advisory lock, keyed on application_id, held only for the auth-side read-check-write. Two concurrent requests serialize there; the second always sees the first's committed total before it validates.

Auth down, core up: billing is unaffected — it reads only budget_usage.ceiling_snapshot, already in core, and never reaches across to auth. Only administration — create, reallocate, release — is blocked until auth recovers. This is the resolution to the open question carried over from the source artifact: enforcement never has a hard dependency on auth's availability.

Core down, auth up: a create or reallocate still succeeds and commits in auth — the ceiling of record is set — but the mirrored snapshot in core can't be written yet. The response says so (syncPending: true) rather than silently claiming full success.

Closing the gap: a sweep, run roughly every 60 seconds, compares api_key.version against budget_usage.ceiling_snapshot_version for every key and re-pushes any mismatch. This bounds staleness to about a minute even when the synchronous push fails, and turns "did the snapshot actually update" from a silent unknown into a counted, alertable metric.

II.6Edge cases

CaseHandling
Key's allocation_pct is NULLNo ceiling at this level; the Application's own ceiling still bounds it. Never treated as zero.
Revoked key still holds a sliceCounts toward the sibling sum until explicitly released — see POST /api-keys/{id}/release-allocation in Part III.
Application's own budget shrinks below its keys' promisesRejected before the requested change is even evaluated — feasibility is checked first, per the source artifact's existing rule.
Reconciliation sweep finds persistent drift on one keyTreated as a signal, not just a fix — logged with a count; repeated drift on the same key points at a bug in the synchronous push, not normal operation.

Part III

IIIAPI contract

Four operations: create a key with an optional allocation, edit one key's allocation, re-slice a whole Application's keys at once, and release a revoked key's frozen slice.

POST/v1/institutions/{tenantId}/api-keys

Create a key scoped to an Application, with an optional share of its budget.

PUT/v1/applications/{applicationId}/key-allocations

Replace every active key's share under one Application in a single call — for a full re-slice, not an incremental one.

{
  "allocations": [
    { "apiKeyId": 4821, "allocationPct": 20.0 },
    { "apiKeyId": 4822, "allocationPct": 30.0 }
  ],
  "expectedApplicationVersion": 7
}

Validated and written exactly as a single-key reallocation, but against the complete sibling set at once — the same evaluation order as Part II.4, run once per row inside one lock.

Return a revoked key's frozen slice to its Application's headroom. Requires the key to already be inactive.
